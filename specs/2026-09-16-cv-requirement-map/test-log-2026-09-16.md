# Live process test, 2026-09-16 — defects found

The owner asked to walk the CV process by hand against a real advert
([System Developer/Tester at Advania](https://jobb.advania.se/jobs/8356906-system-developer-tester-pa-advania)),
with a local folder standing in for Resources, and to keep every defect for fixing afterwards.

**What this test can and cannot show** is written up in the chat, but the short version belongs
here too, because it decides how much the results are worth: the prompt is being followed by a
large model with the whole map in context, while the product runs BYOK models (Mistral Large,
Gemini flash) one item per turn with the server owning the state. A pass here proves the prompt is
*followable* and the wording is right. It does not prove the implementation works.

## Defects

### 1. `analysis-extract.md` uses this very advert as its worked example — CONTAMINATION

The prompt's instructions and its example JSON contain, literally: `"System Developer/Tester på
Advania"`, `"Malmö"`, `"Systemutvecklare"`, `"Praktisk erfarenhet av Java"`, `"Utveckla och
vidareutveckla lösningar i Java"`, `"Arbeta med API:er och integrationer"`, `"Arbeta praktiskt med
testning som en del av teamets leveranser"`, `"Delta i code reviews och teamets gemensamma
utvecklingsarbete"`, `"ansvarstagande"`, `"tar ansvar för att få dina uppgifter framåt"`,
`"Teamet består av cirka 5-6 kollegor"`.

So a model extracting from the Advania advert is shown the answers. Two consequences:

- **Any evaluation on this advert is worthless**, including the one being run today, and including
  the extraction done by hand in this session — it was partly guided by the examples.
- The prompt is over-fitted to one posting. The `core_message` guidance even says "For an advert
  that keeps returning to development and testing together, it is that combination" — which is
  this advert's answer, not a general rule.

**Fix:** rewrite the examples against a synthetic advert in a different field (and a different
language mix), keeping the *shape* of the JSON. Keep one real advert aside, unused by any prompt,
as the evaluation fixture.

### 2. A `flag` is stated and then abandoned

`CvTransitions.analysisSummary` appends `"Одно нужно обсудить сразу: …"` and the turn then moves
straight on to the intake form. The owner's process says a hard condition (citizenship, a stated
number of years, a background check) is **raised with her now** — that is a conversation, not a
line. As built, the condition is mentioned once, no question is asked, and the writer has no
instruction to return to it.

On the Advania advert the flag is `Финальные кандидаты проходят обязательную проверку биографии
(bakgrundskontroll)`.

**Fix:** when the map holds any `extra` with `use = "flag"`, the analysis summary has to END with a
question about it, and step 2 must not be announced in the same turn. Needs a phase or a state
field, because "the flag has been discussed" is currently nowhere.

### 3. The summary's flag sentence reads as a join

`"Одно нужно обсудить сразу: " + flags` puts a capitalised sentence after a colon, and the flag
notes are full sentences written by the extraction. Same for several flags joined by `"; "`.

**Fix:** lowercase the joined notes, or turn the lead-in into its own sentence.

### 4. Twenty competences in one checklist card

The Advania advert yields 7 required competences and **13** `meriterande` ones. As one card that is
two screens of rows, each with a "Partly" button. The API cap (60) does not bite; legibility does.

**Fix:** split the card into "required" and "a plus" groups, or render the `nice` ones as a second
card. The server already stores `weight`, so no schema change.

### 5. "Я прочитал" — masculine self-reference in Russian

`analysisSummary` (ru) says `Я прочитал`. Every Russian server string should be checked for the
same thing.

**Fix:** reword so the agent does not gender itself — e.g. `Объявление прочитано` / `Я закончил
разбор` → `Разбор готов`.

### 6. The intake form never asks for LANGUAGES — and this advert requires them

`CvTransitions.intakeStep` asks for contact, links, employers, education, courses. It does not ask
for languages, and `CvIntakeCheck.PARTS` has no entry for them either, so a form with no languages
is reported complete.

This is not cosmetic on this vacancy. `Goda kunskaper i svenska och engelska` is one of the
advert's **required** competences, and the owner's own CV carries
`Svenska – flytande · Engelska – flytande · Ryska – modersmål` in its header. Taking "the dry
skeleton" as currently defined throws that line away, and the CV then cannot answer a must-have.

A CV's language line is also skeleton by nature — a fact with no story behind it — so it belongs in
step 2 and nowhere else. Step 4 will not recover it: there is no sensible "tell me about a time you
were fluent in Swedish" question.

**Fix:** add `Языки` / `Språk` / `Languages` to the intake list in all three languages, and a
`Languages` part to `CvIntakeCheck` (heading keywords `language|språk|languages|язык`, plus
recognition of a bare line naming a language with a level). Existing intake notes without the
section then correctly report it missing.

### 7. The intake form asks for employers but not for the candidate's OWN PROJECTS

Step 4 explicitly offers three kinds of evidence — `работа, учёба или собственный проект` — and the
writer-method has a whole section on reading a repository. But step 2 asks only for
`Места работы` (employers) and `Ссылки` (links), so an own project arrives, at best, as a bare URL
with no role, no period and no statement of what it is.

The owner's own CV has `Eget projekt: Spira … Pågående sedan 2025` as a full entry alongside the
employers, which is what the skeleton should have carried.

**Fix:** name own projects in the intake list as their own line — what it is, the link, the period —
and treat them as a place of experience everywhere a place is expected, including the per-employer
rule in step 4 (one story per place).

### 8. The finished CV note matches the intake-candidate pattern

`CvApplicationService.INTAKE_TITLE` is `(?iu)profil|профил|мои данные|uppgifter|details|\bcv\b`.
The `\bcv\b` alternative matches the writer's **own output**: the CV note is titled
`CV — <vacancy>`, so once it exists on the goal it is a candidate for "are these your details?".
A second application on the same goal would then offer the previous vacancy's finished CV as the
intake form.

**Fix:** drop `\bcv\b` from the pattern, or exclude any resource already bound as a document of
some application (`cv_note_id`, `letter_note_id`, `analysis_note_id`). The second is the real fix —
a note the app itself wrote for another purpose should never be offered back as intake.

### 9. Server and client disagree about what counts as an intake candidate — an instruction with no button

Server (`CvApplicationService.INTAKE_TITLE`): `profil|профил|мои данные|uppgifter|details|\bcv\b`.
Client (`CvIntakeActions` in `AiPanel.tsx`): `/profil|профил|мои данные|uppgifter|details/i`.

The client's copy has **no `\bcv\b`**. So for a goal whose only matching note is titled `CV …`, the
server reports `intakeStatus = "candidate"` and `CvTransitions.intakeStep` says
*«В ресурсах есть заметка «…» — это ваши данные? Если да, нажмите "Использовать как мои данные"»* —
while `CvIntakeActions` finds nothing and renders no button. The user is told to press a control
that is not on screen, which is the same class of dead end as the silent phases.

**Fix:** the client must not re-derive the candidate. The server already knows which note it meant;
send its id and title in the DTO (`intakeCandidateId`, `intakeCandidateTitle`) and let the button
use them. Two regexes for one decision will drift again whatever is done to them now.

### 10. The collection cards are hardcoded in English while the conversation runs in Russian

`CvCompetenceChecklist` and `CvEvidenceCard` (`AiPanel.tsx`, added today) carry English literals
throughout: "Which of these N do you have?", "Tick what you have. Leave blank what you have not",
"No detail needed yet", "Blank counts as \"no\"", "Partly", "required", "Requirement 3 of 9",
"I have no example for this", "Send", "Save these answers".

Every server-written chat string is localised ru / sv / en through `CvTransitions`, and so is the
step pill. The cards are not — and the cards are where the owner's actual instructions live. In a
Russian session the announcement arrives in Russian and the card directly under it is in English.
The same applies to `CvIntakeActions` ("Details are correct", "Use … as my details"), which
predates today's work.

**Fix:** the card copy belongs to the server, like every other word the process says. Return it
with the step (extend `CvApplicationDto`, or a small endpoint for the current step's card text) in
the conversation language. Hardcoding a second copy of the wording in the client is exactly how the
intake-candidate rule drifted in defect 9 — the same mistake in a different place.

### 11. "Продолжаем" was accepted as confirming the intake, and that is ambiguous

Step 2 is supposed to end only on an explicit confirmation — the "Данные верны" button or
`cv_confirm_intake`. The owner answered "Продолжаем", which says *proceed* but not *the data are
correct*, and it left the turn's actual question (was anything in the Kronofogden CV missing?)
unanswered. It was treated as confirmation here.

Worth deciding deliberately: either a bare "let's go on" counts as confirmation (and then the
prompt should say so, so the writer does not ask twice), or it does not (and then the writer needs
one short re-ask rather than silently advancing). Silently advancing on an ambiguous yes is the
class of behaviour the whole state machine exists to prevent.

### 12. A "Partly" comment can be longer than the card, and it can contain an instruction

The owner's answer for `Linux` was not a word of explanation, which is what the card's own copy
invites ("tell me in a word why"). It was several sentences that (a) denied the competence, (b)
named two places evidence might exist, and (c) **told the writer to go and read the repository and
decide what is relevant**.

Three things follow:

- **The comment field is sized wrong in the copy, not in the schema.** `CvVerdictRequest.comment`
  allows 4 000 characters, so nothing broke; but "in a word why" sets an expectation the real
  answer does not fit, and a two-line textarea makes it worse.
- **A verdict comment can carry a source to read.** `writer-method.md` already requires that a
  source the client points at is read before asking again, but nothing in step 3 does anything with
  a comment except store it — `recordVerdicts` writes `user_answer` and moves on. The pointer would
  have been lost until step 4, or for good.
- **The evidence found is real but belongs to a different category.** The repository shows
  `eclipse-temurin:17-jre` and `node:20-alpine` images, `pgvector/pgvector:pg16`, eight
  `ubuntu-latest` CI jobs with bash steps, and Docker Compose locally. That is "works in Linux
  environments", which answers the *requirement*, not the *competence tag* `Kunskap om Linux`. The
  verdict stayed `partial` on purpose.

**Fix:** reword the card ("если частично — напишите, в чём именно, и где это видно"), grow the
textarea, and have the server notice a comment that names a source. The simplest honest version:
when a `partial` comment is longer than a threshold or contains a URL or a repository name, the
writer is told in its next state block that this comment carries a lead to read.

### 13. A tick and its comment can contradict each other, and the comment has to win

The owner ticked **Azure DevOps** in the checklist and in the same answer wrote *«Azure DevOps не
пиши, а укажи GitHub actions»*. The tick says yes; the sentence says no and names a substitute.

The card has exactly three states — ticked, blank, "Partly" with a comment — and none of them
expresses *"ticked by mistake, and here is the tool I actually use"*. It was recorded as `no`,
following her words, because a tick is a gesture and a sentence is an intention.

**Fix:** let **every** row carry a comment, not only a "Partly" one, and never show the writer a
verdict without the comment that came with it. `CvRequirement` already has `user_answer` for
exactly this; `recordVerdicts` only fills it when the verdict is `partial`
(`v.comment() == null || v.comment().isBlank() ? null : v.comment()` is stored for any verdict, but
the card only offers the field on "Partly"). The gap is in the card, not the schema.

### 14. Nowhere to record an equivalent competence the advert did not name

The advert lists `Azure DevOps`; she uses GitHub Actions and said so. The map holds only what the
advert named, so *"I don't have X, I have the equivalent Y"* has no row to live in.

It matters in two directions at once, and they pull against each other:

- The CV's competence block should say **GitHub Actions**, because that is true and because it is
  what the `CI/CD` must-have is actually answered by.
- `writer-method.md` requires tool names to match the advert exactly, since an automated screen
  matches on them. But writing `Azure DevOps` for someone who does not use it is the one thing the
  method forbids outright. So the exactness rule must not be allowed to manufacture a claim.

**Fix:** a competence row needs an optional `substitute` the user names — stored, shown in the map,
and available to the CV writer, with the rule stated: write the substitute, never the advert's tool
name, when she does not have the advert's tool.

### 12, second occurrence

Two of her four checklist answers (`Linux`, `Bash eller annan scripting`) contain *«проверь
проект»* — an instruction to go and read the repository. That is not an edge case to be handled
defensively; it is how she answers a checklist. It strengthens the fix proposed in defect 12: the
server has to notice a comment that points at a source and tell the writer, in that turn, that
there is something to read.

### 15. Step 4 announces 13 items and then asks 14

`CvTransitions.experienceStep` says *«Я пройду по 8 требованиям и 5 личным качествам — по одному»*
and then ends with *«Начнём с главного требования?»*. The core message is a map item of its own
(`category = "core"`, its own CORE phase) and it is **not** in either count, so the owner is told
thirteen and answers fourteen.

`writer-method.md` is explicit that the writer must never state "a count beyond the one you are
given", precisely so the client can trust the number. A number the server itself gets wrong is
worse than no number.

**Fix:** either count the core item (`«по главному требованию, 8 требованиям и 5 качествам»`) or
drop the numbers from the sentence that already names the core separately. Counting is better — she
asked to see the size of the stack.

### 16. The advert's wording decided a verdict the owner had already answered "no" to

She answered `Bash eller annan scripting` with *«по сути нет»*. But the advert's own tag is "Bash
**or other scripting**", and the project has three PowerShell scripts plus seventeen bash blocks in
CI — so the honest verdict is **yes**, against the requirement as written.

This is not a defect; it is the method working, and it is worth recording as the clearest thing the
test has shown so far. It also says something about the design: **a checklist answered by the user
alone would have lost this competence.** Her "no" was about the word `Bash`; the requirement was
about scripting.

**Implication for the build:** the writer needs the advert's full tag text next to each row when it
reviews the verdicts, not just the short label. `CvMapItem` already carries `quotes`, and the
checklist card shows only `label` — so the card is fine for her, but the *material block* the CV is
written from must show the quote beside the verdict, or this correction cannot happen again.

### 17. The core-requirement card throws away the core message itself

`CvEvidenceCard` titles a `core` item with a fixed sentence — "The most important thing this
employer is asking for" — and renders `item.quotes` below it. `item.label`, which for a `core` row
**is the assembled core message**, is never used. So the card's heading says nothing specific about
this vacancy, and the one sentence the owner most wants to see stated in full appears only in the
chat summary, once, several turns earlier.

Her process is explicit that the core message is assembled from lines scattered through the advert
and then "shown close to the advert's own wording, not retold". Showing the source quotes is right;
dropping the assembled sentence is not.

**Fix:** the card's title is `item.label` (the core message). The generic sentence is already
carried by the kicker above it ("Core requirement 1 of 1"), so nothing is lost.

### 18. One answer carried six stories from five places, and the schema stores one string

Her answer to the core requirement covered: the education (JENSEN, testinriktning), Java and Spring
Boot at **ZoCom**, the **own project** Spira, testing at **Quality Lab**, testing at **Squidler**,
and the Squidler/Replit experiment as a thing of its own.

`CvApplicationService.recordAnswer(applicationId, key, answer)` stores one `user_answer` string,
and `rowsOf(app, key)` writes the **same** string onto every row of the cluster. So five places
collapse into one blob on one item.

This directly defeats the owner's own rule — *"if she has the same requirement at several
employers, each needs its own story or the bullet won't appear under that employer"*. As stored,
the CV writer at step 5 has to re-split this prose by employer and guess which sentence belongs to
which job. That is exactly the guessing the requirement map was built to remove.

**Fix:** an answer needs a place. Either `recordAnswer` takes an optional `place` (employer /
education / own project) and a key can hold several answers, or the card asks per place once it
knows she has more than one. The second is closer to her process: the card already says "tell me
about each separately", so it should provide a field for each rather than one textarea and a hope.

This also means the card's own instruction is currently unanswerable as designed: it asks for
several stories and offers one box.

### 19. Sources named inside an answer are not registered anywhere

She wrote *«смотри соответствующий ресурс Examensbevis and Europass»* and *«ты можешь сам изучить
проект по ссылке … https://github.com/alakhmakova/spira-mindscape»*.

`cv_source_read` exists as a ledger, and `CvAnalysisService.readSourcesForCv` reads sources at the
CV step — but nothing parses an **answer** for sources, and `recordAnswer` stores the text and
stops. So a pointer the user gave in step 4 survives only as prose inside a blob, and whether it is
ever read depends on the writer noticing it several turns later, in a different phase, with the
answer possibly truncated in the material block.

**Fix:** extract URLs and resource titles from an answer at record time into `cv_source_read` as
`pending`, and show the count in the state block ("2 sources named and not yet read"). The
extraction is cheap and does not need a model: a URL regex plus a match against the goal's resource
titles.

### 20. The candidate's OWN motivation has nowhere to live

Unprompted, the owner gave the single strongest piece of letter material there is: she moved from
manual testing into `Systemutvecklare med testinriktning` **deliberately**, to keep testing but at
the automation level and to learn to build products in Java — so the advert's own core (the
combination of development and testing) is answered by her biography, not by a claim.

There is no place to store it:

- `CvApplication` has thirty-odd fields and none for the candidate's motivation. `letter_required`
  and `letter_note_id` are a flag and a pointer to the finished document.
- `cv_requirement.extra_use = 'letter'` is documented in `V26` as "company/team/level notes:
  motivation for the letter" — motivation **extracted from the advert**, not hers. Every
  `cv_requirement` row is derived from the advert by construction.
- The story bank was removed from this flow, so `stories_note_id` is no longer written either.

So her words survive **only in the chat transcript**, and step 6 is two steps away. `ChatHistory.trim`
bounds replayed history by characters and keeps the newest turns, so the longer step 4 runs — and
it has 8 requirements and 5 qualities to go — the likelier this is gone by the time the letter is
written. This is precisely the "things got lost in a long session" failure the whole rebuild was
for.

**Fix:** motivation is user-owned content and needs its own home. Either a `motivation` column on
`cv_application` appended to as she says things, or — better, because she can then edit it — a
user-owned note bound like the others (`cv_document=motivation`), rendered into the map note as its
own section. The map note already reads well with it: a section "Ваша мотивация (для письма)" was
added by hand in this test and is the only reason the text is not already at risk.

### 21. `cv_vision` is a dead column

`V25` adds `cv_application.cv_vision` ("two or three sentences on what this CV has to show —
written once by the analysis") and `CvApplication` maps it. Nothing reads or writes it: `grep` for
`setCvVision` / `getCvVision` across `src/main/java` returns nothing. It is a leftover of the
2026-09-15 design, where the analysis produced a "vision" per application.

Worth stating plainly because it is a near miss, not just dead weight: the name suggests it could
hold defect 20's motivation, and it cannot — it was meant to describe the *vacancy*, and it is
unused either way.

**Fix:** drop the column in the next migration, or give it the job defect 20 needs — but not both
meanings at once.

### 22. The CAR prompt on the evidence card was shorthand, not an instruction

The card said *"Unsure how to tell it? Situation, what you did, how it turned out."* The owner, shown
the Russian rendering, said plainly: **«Это непонятно»**. Three nouns and no verb do not say whether
to pick one, name one or describe one — the mnemonic is written for someone who already knows it.

Her wording, to be used verbatim when the cards are localised (defect 10):

> Не знаете, как рассказать: опишите ситуацию, задачу или проблему, что вы сделали для решения,
> что из этого вышло.

English now reads "Unsure how to tell it? Describe the situation, task or problem, what you did to
solve it, and what came of it." Pinned by an assertion in `cv-collection-cards.test.tsx` so a later
refactor cannot quietly restore the shorthand.

The same check is owed to every other line of card copy: each one should be read as if by someone
who has never seen CAR or STAR.

### 23. "Find it in the project yourself" is the owner's normal answer shape, not an edge case

Third occurrence in four answers: `Linux` ("проверь сам проект и реши, что может быть релевантно"),
`Bash` ("проверь проект, если там есть что-то, что можно вводить"), and now requirement 1 ("найти в
коде проекта или документах и перечислить").

Defects 12 and 19 proposed extracting sources from comments and answers. This raises it from
nice-to-have to required: the writer that cannot do this simply does not answer her. Note also that
the answer she wants is not a document to quote but a **survey** — "list the tools you find" — which
is a repository read with a question attached, not a lookup.

A second thing worth keeping: she answered requirement 1 in **the advert's own verbs** —
`att utveckla` / `vidareutveckla` / `och förvalta tekniska lösningar` — which is ADSS MSP's
self-description from the intro paragraph. That is direct evidence that putting the advert's quotes
beside the question works as designed. The implication for step 5 is that the material block must
preserve her mapping onto those verbs, because the mapping is hers and it is the strongest part of
the answer.

### 24. "The old CV's descriptions are not taken" is unenforceable as built

The intake rule is explicit and the owner repeated it: from an old CV, take the dry skeleton and
**never** its descriptions of the work. The intake note here honours that.

But extracting the skeleton means reading the whole file, so the full CV — every bullet about the
Squidler session bug, the whitepaper, ZoPlanner, the regression cut from five days to three — is in
the model's context for that turn, and then in the conversation history for every turn after it.
Nothing prevents the writer from using those sentences later as if the owner had told it those
stories in step 4. It would look exactly like a correct answer, and it would be the interchangeable
CV she is trying to avoid — assembled from her own old document rather than from the interview.

Observed in this session: the temptation was concrete. The obvious line to play back for
requirement 2 was the regression going from five working days to three, which is a real result — and
it came from the old CV, not from anything she has said here.

**Fix:** this cannot be solved by asking the model nicely, because the text is in its context.
Options, in order of strength: (a) extract the intake skeleton in a **separate, isolated call**
whose output is the skeleton only, so the descriptions never enter the session history at all;
(b) failing that, have `CvFactGate` treat the old CV's prose as NOT part of her evidence corpus, so
a claim traceable only to it is flagged like any invented one. (a) is the real fix; (b) is the net.

### 25. A colleague's own words about her work have nowhere to be marked

Inside the requirement-2 answer: *«Разработчики отмечали хорошее качество моих баг репортов»*.

`writer-method.md` calls a short quotation from a colleague **"the strongest thing a CV can
carry"**, and its question bank has a question aimed at getting exactly this. Yet a
`cv_requirement` row stores only `user_answer` as prose — there is no field, flag or marker for
"this sentence is what someone else said about her". The 2026-09-08 schema had `story_text` and a
behavioural-traits column; the V26 rows dropped both.

So the single most valuable sentence in the answer is indistinguishable from the rest of the blob,
and at step 5 the writer has to find it in prose again. If the material block ever truncates a long
answer, this is the part most likely to go — it sits at the end of a paragraph.

**Fix:** one `user_answer` string is not enough. An answer needs optional named parts — at minimum
`feedback` (what someone else said) and `result` — or a marker applied at record time. This is the
same shortcoming as defect 18 (no place for a story), seen from a different angle: the answer is
stored as undifferentiated text and every structure in it has to be rediscovered later.

### 26. Reading the source corrected a claim the answer implied — the method working, twice now

She wrote that CI/CD is set up "чтобы только работающий и проверенный код попадал на прод, с этой
целью настроено несколько gates". The workflow bears most of that out: `deploy` has
`needs: [frontend, backend, e2e]` and runs only on a push to `main`, and `npm audit` blocks on
`critical` **inside** the `frontend` job, so it gates the deploy too.

But Trivy's `--exit-code 1` on CRITICAL lives in the `dependency-scan` job, and `dependency-scan`
is **not** in `deploy`'s `needs`. So Trivy does not stop a deployment. "Trivy blocks deployment"
would have been false in a way a reader could check in one click.

This is the second time reading the repository changed an answer (the first was `Bash`, where the
advert's own wording turned her "no" into a yes). Two implications:

- The fact gate's real work here is done by **reading**, not by a model being careful. A gate that
  only compares a draft against her typed words would have passed this sentence.
- Step 5 must read the sources **before** writing any line about the project, not check afterwards.
  `CvAnalysisService.readSourcesForCv` already runs at the CV step; what this shows is that it has
  to feed the drafting, and that its findings must reach the material block as facts, not as raw
  file text.

### 27. "Does this count?" is a third kind of answer, and the card has no state for it

Most of her requirement-3 answer was a question: Google authentication — is that an integration?
Several AI providers? The Cloud Run deploy? Connecting Neon? Backend talking to frontend? Ending
with *«Проверь проект и помоги разобраться, что действительно релевантно»*.

The card offers two outcomes: an answer (`record_answer`) or no example (`no_answer`). A request for
a judgement is neither:

- Sent as an answer, a stored question becomes the evidence for that requirement — a question
  masquerading as a story, and at step 5 the writer would draft from it.
- Pressed as "no example", real material is thrown away: she has three good integration stories and
  simply could not tell which of them counted.

And it is not a rare shape. Deciding what counts against a requirement is the writer's expertise,
not hers — `writer-method.md` already splits substance (hers) from wording (the writer's), and this
is the same split applied to **classification**, which the interface does not admit at all.

So the two halves of the trigger diverge: *straight out of study* and *a history that reads thin* are
not the same candidate. **Combination was chosen**, and the one-sentence justification the format
requires was given.

**Fix:** state the trigger as the test, not the life stage — the functional shape is for a history
that reads thin against *this* posting, and recent study is one cause among several rather than the
rule itself. As written, the prompt would have produced a weaker CV for this candidate while
following its own instruction exactly.

### 43. The template's section order contradicts the final check

The template puts `EGET PROJEKT` last, after `SPRÅK`. The check asks: "is the most relevant
experience given the most room?"

For this candidate the own project is the strongest evidence in the document — it is where Java,
tests at every level, CI/CD with gates and the egress investigation all live, and it is the only
place a reader can go and look at the work. Left in its template position it sits below the languages
block, at the bottom of the page.

`EGET PROJEKT` was placed immediately after `ARBETSLIVSERFARENHET`, and the deviation was stated to
her rather than made silently.

**Fix:** the section order needs a rule for this case, not a fixed list. Something as simple as "a
relevant own project sits with the work history when it is the strongest evidence, otherwise after
the languages" resolves it. The current wording forces either a weak document or an undocumented
deviation.

### 44. A side question asked in step 2 was never answered and is now silently lost

In step 2 the folder was seen to hold `Engelska 5.pdf` and `Svenska som andraspråk 1.pdf`, and she
was told they could be added to courses and education. She never answered, and the flow moved on.

Writing the CV, `KURSER` was therefore omitted — not because it was decided, but because a question
fell through. Nothing in the state machine carries an unanswered question forward: the intake step
ended, its transcript scrolled, and the only reason it surfaced again is that the same session wrote
the document.

**Fix:** the step-2 announcement asks one question at a time by design, so a second, optional offer

mechanism.

### 45. Her process says "save the CV and give her the link"; the prompt says nothing is ever saved

`writer-method.md`: "**Everything is proposed, never done.** Every note you write becomes a card the
client approves. Never say a document has been saved when it has only been offered."

Her process for step 5 (2026-09-16): write the CV whole, **format it, save it as a note, say it is
saved, give the link**, ask what to correct, ask whether she wants a PDF.

Both cannot be followed. The prompt's rule is not paranoia — a note genuinely does not exist until
she approves the proposal card, and claiming otherwise was a real defect in the earlier sessions. But
her instruction is deliberate and it is about a different kind of object: the CV **is** the
deliverable of the step, she wants it in Resources where she can open, read and correct it, and an
approval card in front of a two-page document adds a step containing no decision.

**Followed hers** in this run, and the chat said the document is saved.

**Fix:** decide it rather than shipping two rules. The distinction that resolves it cleanly is
ownership: a document the app *produces* — the CV, the letter, the requirement map — is written
directly and reviewed on the saved note; a proposal card stays right for edits to material *she*
owns, such as the intake form or a note she wrote, where the app is changing something of hers. That
is the same line the additive note-editing work already draws, so it needs no new mechanism, only
one sentence in `writer-method.md` saying which side each document falls on.

### Correction to an earlier claim in this log: the JSON-LD does NOT strip the boilerplate

Verified while building the standalone skill. Earlier in this session the chat said the structured

### 46. The app's own output cannot be told from the user's documents by file name

Found while building the standalone skill, on her real folder rather than on a fixture. A reader that
scans her library has to skip what the tool itself produced — reading last week's CV back as evidence
for this week's makes a claim self-confirming. The obvious implementation is a name pattern, and it
fails in both directions at once:

- `cv-exempel.pdf` is **her** reference example of a well-written CV, and it matches a `cv-` prefix.
  Skipping it discards a document she chose to keep.
- The CV written for her today came back into the library as **`CV_Anastasiya_Lakhmakova.docx`**,
  because she opened it in Word and tidied it. Her genuine old CVs are
  `CV_Anastasiya_Lakhmakova_iFACTS.docx` and `Anastasiya_Lakhmakova_CV_Javautvecklare_Kronofogden.pdf`
  — the same shape. No pattern separates them.

**Fix, and it applies to the app as much as to the skill:** record provenance when the document is
created, never infer it when the document is read. In the skill, `write_docs.py` appends every file
it writes to `.cv-writer-cache/generated.json` and the reader consults that list. In the app the
equivalent already half-exists — `cv_application.cv_note_id`, `letter_note_id`, `analysis_note_id`
and `profile_note_id` are exactly this record — which sharpens defect 8: the right test for "is this
note ours?" is whether any application has it bound as a document, not whether its title matches
`INTAKE_TITLE`.

Worth noting how it surfaced: she started using the folder for real mid-session, and the file that
broke the assumption was one she had improved by hand. A fixture would not have contained it.
